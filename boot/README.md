# AI Bootstrap Environment for Free Pascal and mORMot 2

This directory contains bootstrap tooling for AI coding environments that need to build and test this repository's Free Pascal / mORMot 2 code.

> **Path convention:** in this document, `boot/` means this repository's bootstrap directory. It is not the Linux system `/boot` partition.

## Why this exists

AI coding runtimes are often temporary and minimal. A new runtime may have Git, a shell, and a C compiler, but no Free Pascal Compiler (FPC), no mORMot 2 checkout, and no matching mORMot static libraries.

That creates an important failure mode: an AI can review Pascal source code and suggest changes without ever compiling them.

The bootstrap tooling in this directory gives an AI agent a reproducible way to create a usable FPC + mORMot 2 toolchain before modifying Pascal code. The intended workflow is:

1. Bootstrap the compiler and mORMot dependencies.
2. Use the generated compiler wrapper for this repository.
3. Compile relevant changes.
4. Run the project's tests or build commands when available.
5. Do not treat static source inspection alone as sufficient validation.

## Files

### `bootstrap-fpc.sh`

Bootstraps a Free Pascal + mORMot 2 development environment for an ephemeral Linux runtime.

By default it:

- installs the build prerequisites on Debian/Ubuntu-style systems;
- uses the distribution FPC as a bootstrap compiler;
- builds the FPC `fixes_3_2` branch, expected to report FPC 3.2.3;
- installs that compiler into an isolated prefix;
- finds an existing mORMot 2 checkout or clones one into a cache;
- downloads the mORMot POSIX static archive;
- verifies the static archive against mORMot's SHA-256 checksum;
- creates a local `fpc` wrapper next to the bootstrap script;
- performs a small mORMot compilation smoke test.

The script is designed to be idempotent. A fresh runtime performs the complete bootstrap, while a persistent runtime can reuse already-installed and cached components.

### `fpc`

Generated by `bootstrap-fpc.sh`; it should normally **not** be committed.

The wrapper invokes the bootstrapped FPC with the correct private FPC configuration, mORMot unit search paths, and matching static-library path. Using the wrapper also avoids accidentally mixing the custom compiler with a system-wide FPC configuration from another FPC version.

Add it to `.gitignore`, for example:

```gitignore
/boot/fpc
```

## Usage

From the repository root:

```bash
chmod +x boot/bootstrap-fpc.sh
boot/bootstrap-fpc.sh
```

Verify the compiler:

```bash
boot/fpc -iV
boot/fpc -iTP
boot/fpc -iTO
```

Compile a Pascal program:

```bash
boot/fpc path/to/project.lpr
```

If the repository already has a build or test script, prefer that workflow and configure it to use `boot/fpc` where possible.

## Recommended instruction for AI agents

Repository/project instructions can contain the following rule:

> Before working on Pascal or mORMot 2 code, run `boot/bootstrap-fpc.sh`. Compile all relevant changes with `boot/fpc` and fix compiler errors before giving the final answer. Do not rely only on static analysis. Prefer the repository's existing build and test scripts when available, using `boot/fpc` as the FPC compiler.

This instruction is intentionally written so it can be used with ChatGPT, coding agents, CI-like sandboxes, or other AI development environments that provide a Linux shell.

An AI agent should not assume that a compiler installed during an earlier conversation or runtime still exists. It should check or rerun the bootstrap when entering a fresh environment.

## Useful environment overrides

The bootstrap script can be customized with environment variables:

| Variable | Purpose |
| --- | --- |
| `FPC_REF` | FPC branch or tag to build. Default: `fixes_3_2`. |
| `FPC_EXPECTED_VERSION` | Version expected after the FPC build. Default: `3.2.3`. |
| `FPC_PREFIX` | Installation directory for the custom FPC toolchain. |
| `FPC_CACHE_DIR` | Cache location for source trees and downloads. |
| `FPC_REFRESH=1` | Refresh/rebuild cached FPC sources and installation. |
| `FPC_JOBS` | Number of parallel jobs used while building FPC. |
| `MORMOT2_DIR` | Path to an existing mORMot 2 checkout. |
| `MORMOT2_REF` | mORMot branch/tag for the cached checkout. Changing it switches the cached clone to that ref. |
| `MORMOT2_REFRESH=1` | Refresh the cached mORMot checkout even when `MORMOT2_REF` is unchanged. |
| `MORMOT2_STATIC_URL` | URL of the matching `mormot2static.tgz` archive. |
| `MORMOT2_SKIP_STATIC=1` | Skip downloading mORMot static object files. |
| `MORMOT2_SKIP_SMOKE_TEST=1` | Skip the final bootstrap compilation test. |

Examples:

```bash
FPC_JOBS=4 boot/bootstrap-fpc.sh
```

```bash
MORMOT2_DIR="$PWD/vendor/mORMot2" boot/bootstrap-fpc.sh
```

```bash
FPC_REFRESH=1 boot/bootstrap-fpc.sh
```

## Runtime assumptions

The bootstrap script is primarily intended for disposable Linux coding environments and currently expects an `apt`-based distribution when packages need to be installed.

A fresh environment generally needs:

- network access to the configured package repositories;
- network access to the FPC and mORMot sources/downloads;
- `root` privileges or `sudo` for package installation;
- enough CPU, memory, and disk space to build FPC.

If those capabilities are unavailable, the AI should report that limitation rather than claiming that compilation succeeded.

## Cache and installation locations

Unless overridden, cached sources and downloads are stored below:

```text
~/.cache/mormot2-fpc/
```

When running as root, the custom FPC installation defaults to:

```text
/opt/fpc-fixes-3.2/
```

For a non-root user it defaults to:

```text
~/.local/fpc-fixes-3.2/
```

These locations are runtime artifacts, not repository source files.

## Why use the wrapper instead of plain `fpc`?

A runtime can contain more than one FPC installation. In particular, the system compiler may be FPC 3.2.2 while this bootstrap builds the mORMot-oriented `fixes_3_2` compiler.

Running plain `fpc` can therefore pick up the wrong executable or `/etc/fpc.cfg`, producing subtle compiler/unit mismatches.

`boot/fpc` pins the compiler and its configuration and adds the mORMot source/static paths required by the bootstrapped environment. For automated work in this repository, it is the preferred compiler entry point.

## Guidance for AI-generated changes

After bootstrapping, an AI agent working on Pascal code should, where practical:

1. Compile the directly affected program, unit, package, or test target.
2. Resolve all compiler errors caused by its changes.
3. Run relevant automated tests when the repository provides them.
4. Distinguish compilation success from test success in its report.
5. Mention any validation it could not perform because of missing services, platforms, credentials, network access, or other runtime constraints.
6. Avoid claiming that code is correct solely because it looks syntactically or logically plausible.

The bootstrap does **not** replace the repository's own build system. It provides the compiler/runtime foundation that lets an AI use that build system reliably.

## Security and reproducibility notes

The bootstrap installs packages and downloads/builds third-party source code. Review the script before using it in security-sensitive or production environments.

The mORMot static archive is checksum-verified against the selected mORMot checkout. For highly reproducible builds, also pin `FPC_REF`, the mORMot revision, and dependency URLs/revisions used by your project instead of following moving branches indefinitely.

## Human developers

The tooling is useful outside AI environments as well. It can provide a known compiler baseline for reproducing an AI-reported issue, checking a clean-room build, or comparing behavior with a developer's locally installed FPC toolchain.

The key idea is simple: **Pascal changes should be compiled, not merely inspected.**
